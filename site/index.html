            A snapshot is v86 save_state(): CPU, devices, VGA memory and all guest RAM, compressed with LZ4 level 1 in a Worker, so saving does not stall the page. After the first snapshot of a kernel, a snapshot keeps only the 4 KiB pages of RAM that changed since the last one saved or restored (a delta, found by hashing every page) and Restore puts them on top of that one's RAM. A download is the full state as an LZ4 frame that lz4 -d reads. Snapshots are stored in this browser (IndexedDB) and kept across reloads, each for the kernel it was taken with (the bzImage's SHA-256); tap a name to rename it.

            What this page remembers in this browser (localStorage, and IndexedDB for imported DWARF). Nothing is sent anywhere. A change takes effect at once.
            
  
            Tabs
            
  
            
    
    The tab buttons show only their emoji; hover, focus or a long press shows the name. On by default on screens up to 400 px wide, where the names take three rows.
  
            
  
            Running
            
  
            
    
    The speed in the Machine tab: BIOS and setup are stepped as fast as possible, then the kernel runs at this speed. Changing it there changes it here. ?speed= in the URL overrides it for one visit.
  
            
  
            
    
    Guest time while the page steps the CPU: a virtual clock of this many instructions per microsecond, or real time (the clock in the Machine tab). ?mips= in the URL overrides it.
  
            
  
            
    
    The count box in the Machine tab: at full speed, first step the whole boot in the background, counting, then run the JIT. ?count=0 in the URL turns it off for one visit.
  
            
  
            Remembered for each kernel
            
  
            
  
            Reset
            
  
            
    
    Forgets everything on this tab and goes back to the defaults. The offline copy of the site (service worker cache) stays.
    
  
            

            


            
  
            This page boots a Linux-style bzImage in v86, an x86 emulator compiled to WebAssembly, and lets you look inside the machine while it runs. Four kernels come with it: hello, a toy kernel that prints two lines and halts; minified-linux, the reduced Linux kernel of minimal-kernel-build; and Debian 6.1 686 (bookworm's linux-image-6.1.0-50-686), once without an initrd (it ends in a root-fs panic) and once with its initramfs (it stops at the BusyBox shell). All four come with their debug info (DWARF): file:line, C source, variables, backtraces, parameters and locals, task names and a coverage tree. Any bzImage can be loaded from disk.
            
  
            Tabs
            
  
              
    
            • Machine: the VM's screen, Pause, Continue, Step, speed, clock, count, the state line and the counters, then what runs and how it boots: the kernel, RAM, a bzImage from disk, symbols, C source, initrd, command line, Boot, the loaded bzImage's header and build. It opens first. On every tab the menu toggle at the bottom right shows whether the VM runs and how fast; its menu has Back and Forward, the run state with the instructions stepped (a click opens the Machine tab) and Pause or Continue. The VM keeps running and its screen keeps changing while another tab is shown; keys go to the VM only while the Machine tab is shown.
              • 
    
            • Memory: the physical memory map from the boot header and one square per 4 KiB page, coloured by region and ELF section, with the pages of EIP and ESP marked.
              • 
    
            • Page: one page as a single listing, instructions where the kernel has code and hex rows elsewhere, with symbol headers; after each instruction its jump paths in and out (static and observed while stepping, with counts), and the jumps inside the page as arcs.
              • 
    
            • Debugger: registers, stepping and run-to-address; at a pause the C line and inlined-at chain of EIP, the running task (comm, pid), the call stack unwound with the DWARF call frame information, each frame's parameters and locals, and the kernel's global variables, pretty-printed from guest RAM.
              • 
    
            • C source: the Page listing and the Debugger interleave the C lines (from the DWARF of a -g build with byte-identical code) with the instructions; tap one for the function with its executed lines. The text is shipped for every sample kernel (Debian: its source package); for an imported vmlinux pick its source folder or .tar.
              • 
    
            • Symbols: import a System.map or an unstripped vmlinux for the current kernel (Machine tab, or drop it on the page with a bzImage from any tab); it replaces the kernel's symbols everywhere.
              • 
    
            • initrd, cmdline (Machine tab): pass an initrd and a command line to v86 for third-party 32-bit kernels (v86 puts the initrd at 64 MiB, so RAM is raised to fit). Our kernels ignore a bootloader initrd.
              • 
    
            • Calls: the symbols the CPU went through while stepping and the transitions between them, live, with task switches named by task.
              • 
    
            • Source: all the kernel's code as a tree of directories, files and functions with the lines and instructions that ran while stepping (coverage); a file opens in the Source panel with its executed lines, lcov export.
              • 
    
            • Snapshots: save, name, restore, download and diff the whole machine state; kept in this browser across reloads.
              • 
    
            • Settings: what the page remembers in this browser (compact tabs, speed, clock, count, and per kernel imported symbols, command lines, watch expressions and measured boot lengths), each with an explanation and Forget, and Reset all settings.
              • 
  
            
  
            Counting and stepping
            
  
            v86 normally runs guest code through a JIT, at least 100,003 instructions per call, and has no single-step API. The page adds two exports to v86's own v86.wasm at load time (the functions are already in it and named in its name section, the code is unchanged): read_imm8, which fetches the byte at EIP, and the interpreter's run, which executes one instruction. Stepping calls them from JavaScript the way v86's interpreter loop does. By default every boot steps BIOS and setup as fast as possible to the kernel entry at 0x100000, then the kernel runs at 1k instructions per second, counted live, until "Hello, World!" and "Still alive" are both in VGA text memory at 0xb8000 (hello: 154 instructions, a fraction of a second; the minified Linux: about 132,000 instructions, 2 minutes 12 s, with an ETA). With speed set to full (remembered, or ?speed=full) and count on, the whole boot is stepped in the background first and then runs on v86's JIT.
            
  
            The counts are exact for the run shown. A rep string instruction counts once per v86 entry, and v86 runs at most a page of iterations per entry. On the virtual clock (on by default) every count is the same in every run, from reset and from the kernel entry, at any stepping speed and at full JIT speed: the timer follows the instruction count, the RTC starts at a fixed date, RDRAND and the network card's MAC address come from a seeded generator, and Debian's panic and prompt stops land on an exact instruction. Keys typed there are recorded with their counts, and Replay puts them in again at the same counts. The clock rate changes the from-reset count, since SeaBIOS's waits take more instructions at a faster clock. A run at full JIT speed gets its timer interrupts at the ends of its slices, so its counts differ from a stepped run's; each of the two repeats exactly. With the real-time clock the counts change from run to run: SeaBIOS waits on wall time, a kernel that calibrates delay loops against the timer counts differently at each speed, and typed keys go in when they arrive. hello's kernel count matches qemu instruction for instruction. site/README.md has the cross-check against qemu.

            Memory tab
            
  
            One square per 4 KiB page, coloured by region of the boot memory map or by the kernel's ELF section:
            
  
              
  
                
    
              • EIP
      Blue box around a page's square, with the EIP label left of its row: the page of the next instruction, at its physical address (through the page tables once paging is on), the one the Debugger shows. The line above the grid says where EIP is and opens it in the Page tab. It follows EIP while stepping and when paused; at full speed (JIT) it is drawn when the CPU stops. Where: Memory tab.
