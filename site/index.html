      This page boots a Linux-style bzImage in v86, an x86 emulator compiled to WebAssembly, and lets you look inside the machine while it runs. Four kernels come with it: hello, a toy kernel that prints two lines and halts; minified-linux, the reduced Linux kernel of minimal-kernel-build; and Debian 6.1 686 (bookworm's linux-image-6.1.0-50-686), once without an initrd (it ends in a root-fs panic) and once with its initramfs (it stops at the BusyBox shell). All four come with their debug info (DWARF): file:line, C source, variables, backtraces, parameters and locals, task names and a coverage tree. Any bzImage can be loaded from disk.
      
  
      Tabs
      
  
        
    
      • Memory: the physical memory map from the boot header and one square per 4 KiB page, coloured by region and ELF section.
        • 
    
      • Page: one page as a single listing, instructions where the kernel has code and hex rows elsewhere, with symbol headers; after each instruction its jump paths in and out (static and observed while stepping, with counts), and the jumps inside the page as arcs.
        • 
    
      • Debugger: registers, stepping and run-to-address; at a pause the C line and inlined-at chain of EIP, the running task (comm, pid), the call stack unwound with the DWARF call frame information, each frame's parameters and locals, and the kernel's global variables, pretty-printed from guest RAM.
        • 
    
      • C source: the Page listing and the Debugger interleave the C lines (from the DWARF of a -g build with byte-identical code) with the instructions; tap one for the function with its executed lines. The text is shipped for every sample kernel (Debian: its source package); for an imported vmlinux pick its source folder or .tar.
        • 
    
      • Symbols: import a System.map or an unstripped vmlinux for the current kernel (next to From disk, or drop it on the page with a bzImage); it replaces the kernel's symbols everywhere.
        • 
    
      • initrd, cmdline: pass an initrd and a command line to v86 for third-party 32-bit kernels (v86 puts the initrd at 64 MiB, so RAM is raised to fit). Our kernels ignore a bootloader initrd.
        • 
    
      • Graph: the symbols the CPU went through while stepping and the transitions between them, live, with task switches named by task.
        • 
    
      • Coverage: all the kernel's code as a tree of directories, files and functions with the lines and instructions that ran while stepping; a file opens with its executed lines, lcov export.
        • 
    
      • Snapshots: save, restore and download the whole machine state.
        • 
  
      
  
      Counting and stepping
      
  
      v86 normally runs guest code through a JIT, at least 100,003 instructions per call, and has no single-step API. The page adds two exports to v86's own v86.wasm at load time (the functions are already in it and named in its name section, the code is unchanged): read_imm8, which fetches the byte at EIP, and the interpreter's run, which executes one instruction. Stepping calls them from JavaScript the way v86's interpreter loop does. By default every boot steps BIOS and setup as fast as possible to the kernel entry at 0x100000, then the kernel runs at 1k instructions per second, counted live, until "Hello, World!" and "Still alive" are both in VGA text memory at 0xb8000 (hello: 154 instructions, a fraction of a second; the minified Linux: about 132,000 instructions, 2 minutes 12 s, with an ETA). With speed set to full (remembered, or ?speed=full) and count on, the whole boot is stepped in the background first and then runs on v86's JIT.
      
  
      The counts are exact for the run shown, with two caveats: a rep string instruction counts once per v86 entry, and v86 runs at most a page of iterations per entry; SeaBIOS waits on real time, so the part before the kernel varies between runs; and with the real-time clock a kernel that calibrates delay loops against the timer counts differently at each speed (the virtual clock, on by default, avoids that). hello's kernel count is the same every run and matches qemu instruction for instruction. site/README.md has the cross-check against qemu.
